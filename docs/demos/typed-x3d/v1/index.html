    What the corpus caught in our own generator
    
      
    The first run had one split: Zod rejected TransmitterPdu.x3d, the other three accepted it. @geoSystem is a JSON Schema tuple (prefixItems of 4, minItems 2), and Zod's tuple demands every position. The generator now marks positions at or past minItems optional and states the length bounds the tuple cannot. A regression test draws 400 random arrays against each of the 79 tuple-typed fields and compares Zod with ajv.
    
      
    Fuzz, seed 1: 7,728 mutants of 966 valid scenes
    
      
    
      
    One real limit
    
      
    Zod validates by recursive descent. At Node's default stack, a scene nested 240 Transforms deep (two adversarial fixtures) overflows it while ajv is fine. The library reports it as not checked, never as valid.

    5. Honest limits
    
  
      
    
    • The Web3D JSON Schema is marked experimental and stops at X3D 4.0. A model that writes 4.1 content (GaussianSplats, PeriodicWave) is told "no", correctly for the file as published and wrongly for the draft standard. The gate says which standard it vouches for.
      • 
    
    • It does not see ROUTE targets, DEF/USE order, profile and component declarations or what a scene looks like. Those need the semantic checks and a renderer; the table above shows each doing a job the others cannot.
      • 
    
    • The converter from XML to JSON is ours (schema-driven, 97 files could not be converted, 8 more contain NaN or Infinity and are not JSON). Counts in the corpus tiles are over the 1,428 it could convert, and 578 of those had at least one attribute or child it could not place, which the schema then judged as written.
      • 
    
    • Timings are one software-only container, not a benchmark rig.
