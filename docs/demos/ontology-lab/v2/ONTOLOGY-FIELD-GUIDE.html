02 / Five questions that must stay separate

A validation ladder is a set of instruments.

QuestionInstrumentWhat a pass does not establish
Did the XML parse?An XML parser, with an explicit entity and DTD policy.Correct X3D structure, scene coherence, or a useful image.
Does the source follow its X3D gate?The selected XSD, X3DUOM-informed checks, and semantic diagnostics.Task completeness, visual quality, or every intended property.
What follows from the graph?An identified reasoning profile over identified graph inputs.Whether the original source was legal or the inferred categories were intended.
Does this graph satisfy these constraints?A shapes graph, an entailment policy, a SHACL engine, and a severity policy.A universal correctness verdict independent of those inputs.
Can we trust this account?Available source bytes, hashes, witnesses, receipts, and an authenticated provenance channel where required.Authenticity from a hash alone.

The supplied fault bench is valuable because different layers catch different losses: a missing geometry, a dangling ROUTE, a wrong-type USE, an invalid placement, a forward USE, and a duplicate DEF do not become one problem merely because they all affect the same scene.

03 / The ontology proposes a classification

Domain and range infer membership. They do not grant placement permission.

Under RDFS, a property use can infer a subject type from its domain and an object type from its range. Several declared domains or ranges apply together. They do not describe a menu of alternatives. [1]

@prefix ex: <urn:example:> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .

ex:slot rdfs:range ex:Child, ex:Visible .
ex:parent ex:slot ex:box .

# RDFS entails BOTH classifications:
ex:box a ex:Child, ex:Visible .

This tiny example explains the mechanism behind the study's more dramatic over-typing exhibits. It is not evidence that every ontology or every RDFS application is defective. The concrete counts in the study belong to its pinned inputs, rule profile, and receipts.

Question A / Reverse lookup

Which ranges already subsume Box?

A placement map can compare Box's existing superclasses against declared property ranges. In the supplied tool findings, X3DNode is the broad named range explaining one such match. The map's exclusions and counting rule matter.

Question B / Forward inference

What type follows after using a property?

Given a hasChildren statement, RDFS applies every declared range whether or not the object started as a subtype. The supplied slice includes a child-node range. A reasoner can therefore infer the very type a subsequent class constraint asks for.

These are different computations. Replacing the forward-inference explanation with the reverse-map counting result would create a new error while trying to correct an old one.

The useful counterfactual

Keep the asserted graph fixed. Validate it once without adding range entailments. Then materialise the chosen rules into a separate copy, inspect the added type statements, and run the same constraint again. If a violation disappears without a source edit, the interpretation changed. The source was not repaired.

A narrower report is not automatically a better scene. Inference may satisfy one constraint while expanding the target population of others. Compare individual focus nodes and constraints, not just the final number of findings.

Measured with a second engine (17 Nov 2026): the same F5 graph, ontology slice and lab shapes in pyshacl 0.40.2 with full RDFS inference (owlrl 7.6.2). Without inference: one result, the Box under ChildrenAreChildNodesShape. With RDFS: that result is gone, and 57,769 new results appear on 142 focus nodes (57,674 from ContainmentDomainShape, 95 from ShapeGeometryShape), all created by inferred types. One real fault hidden, tens of thousands of artefacts added, and no byte of the source changed. The workbench's installed N3 rule subset shows the hiding (S7 1 → 0) on a smaller rule set; the full closure shows the widening as well.

SHACL has its own contract

SHACL validates a data graph against a shapes graph and returns structured results. Record the shape, focus node, path, severity, and message; keep execution failure separate from a completed validation. Also state the application's severity policy. A tool-level success flag is not a clean-scene flag. [5]

{
  "execution": "completed",
  "validation": { "conforms": false, "violations": 1 },
  "evidence": { "inputs_available": true, "recomputed_here": true }
}

This is a recommended result contract for an integration, not the exact output of every engine in the package.

04 / Order and identity are data

A colour is a sequence of components.

RDF graphs are sets of triples. An ordered collection is represented by a structure such as linked rdf:first/rdf:rest cells; the list's order is in those links, not in Turtle line order. A graph also cannot recover distinctions that its conversion never encoded. [2]

The colour-list experiment separates two losses. In the newly checked bundled engine, the plain SELECT ?m ?c list-path query preserves all three occurrences of Pearl's value 1; adding DISTINCT collapses them. Neither value-only result supplies an RGB position. Query the cells or explicitly bind each fixed component. An ORDER BY controls a result sequence; alphabetically sorting JSON rows afterwards changes that answer. [3]

# A fixed three-component colour, with position carried by the pattern:
?material x3do:diffuseColor ?head .
?head rdf:first ?red ; rdf:rest ?cell1 .
?cell1 rdf:first ?green ; rdf:rest ?cell2 .
?cell2 rdf:first ?blue ; rdf:rest rdf:nil .
(1 1 1)≠{ 1 }DISTINCT can collapse equal values; positions are a separate concern.

A correction worth teaching: the historical F-08 finding describes the recorded server result. It must not be promoted into a blanket claim that every SPARQL list-path query removes repeated values. The new local regression distinguishes plain SELECT multiplicity from DISTINCT and from missing order.

Preserve terms before formatting them

CasePreserveAvoid
Unbound variableAn explicit unbound state, such as JSON null in a display contract.An empty string, which is a possible literal value.
Blank nodeDistinct answer-local labels plus the blank-node term kind.One shared _:blank label for every node, or assuming a label is stable across independent parses.
Typed literalLexical form, datatype IRI, and language when applicable; a numeric convenience value only when safe.Converting every number to a JavaScript Number and silently rounding large integers.
Ordered queryThe engine's result sequence, including multiplicity.Sorting for display and then treating the first row as the original query's winner.

Source identity survives where graph identity cannot

Reproduced in this enhancement: the supplied Cabinet and F6 Turtle graphs have the same bounded graph fingerprint, while the XML audit reports a forward USE only for F6. This is evidence of information lost by that projection. The reports inspect XML and Turtle independently; their derivation correspondence was not rerun. The algorithm is semantic-twin-graph-c14n/v1, not RDFC-1.0. See companion/examples/cabinet-audit.json and fault-F6-audit.json.

A forward USE and a backward USE can project to the same relationship when source order is omitted. Duplicate DEFs may collapse onto one IRI. A positional IRI can change after an insertion—or survive while naming a different source node. Treat a source locator as a versioned witness: document hash, node selector, source span, and expected original text. Use persistent authoring identifiers where the application needs identity across edits.

Do not infer source legality from graph coherence. A projection can erase the evidence needed to reject the original document. Preserve and check both representations.

05 / Evidence you can actually inspect

A matching hash answers a narrow, useful question.

StatusMeaning in this editionNext useful question
Computed locallyThe current code ran against available inputs and recorded a result.Which inputs, profile, engine, and limits produced it?
Verified shipped bytesAvailable file bytes match a stated digest.Who supplied the digest, and is that channel trusted?
Recorded observationA supplied historical receipt describes a run elsewhere or earlier.Are the raw inputs and environment available to reproduce it?
Referenced but absentThe receipt names a source, schema, raw log, or build item not in this package.What must be supplied before independent verification is possible?

The original manifest contains both a shipped-file digest and a source digest. Some published files were transformed; those two hashes need not be equal. Verifying the shipped copy does not regenerate the missing source or prove the transformation. Preserve both identities and explain the relationship.

Source hash

Did these exact bytes change?

Whitespace, quote style, comments, or attribute order can change this hash even when the RDF graph is isomorphic. This is the right guard for a minimal source edit.

Graph hash

Did this RDF structure change?

A declared canonicalisation algorithm can make blank-node relabelling irrelevant. Name the algorithm and its limits. A project-specific bounded algorithm is not automatically interoperable with RDFC-1.0.

The W3C RDF Dataset Canonicalization Recommendation defines RDFC-1.0 for canonicalising RDF datasets. Use a conformant implementation and test corpus when interoperable signatures or identifiers depend on that standard. The companion's bounded graph fingerprint is a separately named reference technique. [4]

Integrity is not authenticity. A hash chain detects edits relative to a trusted root or known head. If an attacker replaces both the content and every expected hash, an unsigned bundle cannot authenticate its original publisher. Keep the chain useful without claiming more.

A small receipt can still be informative

{
  "claim": "one selected colour value was replaced",
  "input_sha256": "…",
  "output_sha256": "…",
  "instrument_sha256": "…",
  "profile": "minimal-attribute-edit",
  "scope": "source edit only; RDF conversion not rerun"
}

Referencing an instrument dictionary by hash avoids copying the same engine and input metadata into every ledger record. The verifier must also reject missing dictionary entries, modified payloads, reordered records, and an unexpected final head. A valid chain remains an integrity statement, not a claim that the observation itself was true.

06 / A repair should have a witness

Change the intended bytes. Show the untouched assumptions.

The supplied findings show why full-document reserialization can obscure a tiny X3D material edit: it can rewrite quotes and formatting, and dropping a DOCTYPE can change a later conversion pipeline's defaults. A repair demonstration should preserve the document's surrounding bytes and retain an explicit DTD policy.

  1. Bind the edit to a source version.Require an exact input SHA-256. A selector without a version guard can point at stale text.
  2. Resolve one unambiguous target.Identify the element and attribute. Reject duplicate DEF matches, missing fields, or an unexpected old value instead of guessing.
  3. Replace only the intended attribute value.Preserve surrounding bytes, quoting, the XML declaration, comments, and a DOCTYPE when present. Do not fetch external entities to perform the edit. A minimal patch cannot recover an already removed declaration or its defaults.
  4. Emit the source witness.Show the selector, span or line information, old and new values, changed-byte extent, and before/after hashes.
  5. Recheck the representations you actually changed.Parsing, X3D schema validation, semantic diagnostics, graph regeneration, SHACL, and rendering are separate steps. Mark every skipped step.

The browser F1 demonstration has a deliberate boundary: its minimal Ruby colour edit is paired with separately evaluated RDF facts for the repair fixture. It is not a full general-purpose XML-to-RDF converter, and it must not be described as a completed source-to-graph regeneration pipeline.

Use the companion's tested local primitives as integration examples. They demonstrate source guards, graph fingerprints, and compact evidence chains.

Now in x3d_mcp (17 Nov 2026): the guarded edit and the witness audit are server tools. patch_x3d_attribute refuses a stale source hash, an ambiguous DEF or an unexpected old value, keeps every other byte, and then re-runs the XSD and validate_semantic on the edited bytes, the step the companion leaves to the pipeline. source_witness_audit returns byte-located DEF/USE/ROUTE witnesses. shacl_counterfactual runs the same shapes on the asserted graph and after inference and lists what was hidden and what was added. The stdio fork hang (F-01) was fixed separately in x3d_mcp PR #18.

07 / Agent assistance with an accountable boundary

Shapes can describe the task without becoming authority.

As checked on 14 November 2026, SHACL 1.2 Core is a W3C Working Draft dated 10 November 2026. Its sh:agentInstruction property appears among non-validating shape characteristics and carries natural-language guidance. It is not itself an executable constraint, an instruction-priority mechanism, or permission to act. The bundled engines must not be assumed to implement the draft's new features. [6]

Agent-facing

A concise repair brief

Describe the intended outcome, permitted scope, focus node, field, expected old value, and a small candidate change. Carry source and shapes hashes with the brief.

Machine-facing

A repeatable acceptance check

Execute named constraints with bounded resources. Return explicit execution, conformance, and evidence statuses. Keep the generated change reviewable before any publication or external write.

The recorded sessions show particular tool interactions on particular pinned versions. They are useful case studies. They do not establish that grounding improved an LLM's reliability without a controlled comparison. A strong next study would define a fault corpus, a baseline, task outcomes, failure categories, and the exact evidence supplied to each condition.

A contract for a useful semantic tool

  • Preserve RDF term kind, lexical value, datatype, language, unbound state, and result order.
  • Separate the identity of source bytes, parsed graph, rule profile, shapes, and result payload.
  • Report limits and truncation. A complete-looking page must not silently represent a partial answer.
  • Use a killable worker or process for an actual deadline. A timer sharing a blocked execution thread is not a hard timeout.
  • Give a source witness and a minimal change proposal. A vague message about a class is not an edit location.
08 / Six experiments worth keeping

Predict the outcome before running the instrument.

01 / Beginner

Three ones are still three components

Inspect a white material as an ordered list. Compare plain SELECT, SELECT DISTINCT, and indexed cells. Confirm where multiplicity survives and why values without indices cannot reconstruct an RGB vector.

Evidence: cell order, repeated values, query text, and result terms.

02 / Intermediate

A classification that hides a fault

Run the same child-node constraint on asserted data and after range entailment. Find the added type edge that changes the verdict. Do not change the source.

Evidence: asserted hash, rules hash, derived delta, and per-constraint result.

03 / Intermediate

Same graph, different text

Change Turtle whitespace and blank-node labels in a small fixture. Compare byte hashes with declared graph fingerprints. Then change one literal and repeat.

Evidence: different source digests, graph-equivalence result, algorithm name.

04 / Advanced

The ambiguous identity

Inspect the supplied forward-USE and duplicate-DEF variants. Identify which source fact the RDF projection omits or merges. Name the additional witness needed.

Evidence: source order or uniqueness check beside graph relationships.

05 / Advanced

One attribute, one reviewable patch

Use the guarded repair fixture. Try the correct source hash, then a stale one. Confirm the stale edit is rejected. With a synthetic fixture that contains a DOCTYPE, confirm that the edit preserves it; the packaged F1 browser fixture has no DOCTYPE to preserve.

Evidence: source guard, target, changed span, and output digest.

06 / Builder

A receipt that refuses overclaiming

Verify available files, then inspect a historical reference absent from the package. Record the first as a matching local digest and the second as unavailable.

Evidence: verified, mismatched, and unavailable are distinct states.

A bounded research programme

PriorityNext implementationCompletion evidence

The strongest semantic twin is one that helps you locate why two answers disagree.
