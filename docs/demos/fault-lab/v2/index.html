One small heritage twin of the Giza plateau: an X3D scene joined to a CIDOC-CRM record. We broke it ten ways, one edit each, the way real files get broken. Then we asked every checker, before and after the ontology review fixes, and carried each broken file into glTF and USD to see what the downstream tools say.

Each of the seven faults that live in the X3D file was converted to glTF and to USD, then handed to that format's own validator. A fault is erased when the converted file is identical to the clean twin's: the mistake is gone from the file and so is every chance of finding it. It is carried when it travels.

What this does not show

  • One fault is still missed. Giza's latitude and longitude are both under 90, so swapping them gives a legal coordinate about 230 km away. A range check cannot see it. It needs a second source for where the site is.
  • Planted, not found. We wrote these ten faults ourselves. The catch rate says the checks work on these kinds of mistake, not that 90% of real mistakes are caught.
  • The strict record shapes are hand-written for this twin's case (x3d_mcp shapes-strict.ttl). The cardinality and coordinate checks are general.
  • The USD converter is this demo's own, built to measure what USD can hold. It is not a general exporter.
  • Pixel counts are from software rendering (SwiftShader). A GPU will differ by a few pixels at edges.
  • Blender's USD exporter still carries none of the metadata, and its glTF exporter carries it as plain extras, not as semantic packets. Host DEF names come back from Blender with OB_ and MA_ prefixes.
  • The Blender rows use the add-on from x3d-blender-io PR #70. v1 of this page keeps the measurement from before that fix (0 of 3 trees).
